# ADR 0006: Per-record envelope encryption of PII with an env-managed master key

- **Status:** Accepted
- **Date:** 2026-04-25
- **Supersedes:** [ADR 0005](0005-pii-envelope-encryption-kms.md)

## Context

ADR 0005 mandated AWS KMS for envelope encryption. The Director has
since constrained Phase 1 to **free-tier hosting only** while the
centre is small (~30 students). KMS, plus the IAM and AWS account
overhead it requires, is out of scope at this stage.

The encryption requirement itself does not change: a raw `pg_dump`
must reveal **zero** identifiable PII. The only thing that changes is
where the wrapping key lives and how DEKs are wrapped.

## Decision

Replace KMS with an **env-managed master key** that wraps per-record
DEKs locally. The wire format remains versioned so we can promote back
to KMS (or any HSM) later without a data migration.

- **Master key**: `OASIS_MASTER_KEY` (32 random bytes, base64). Lives
  only in Vercel project env, GitHub Actions secrets, and `.env.local`
  for development. Never in the database, never in source.
- **Master key version**: `OASIS_MASTER_KEY_VERSION` (e.g. `1`). The
  active version used to wrap new DEKs. Older versions are kept
  available as `OASIS_MASTER_KEY_V<n>` so existing ciphertexts decrypt
  during rotation.
- **Per-record DEK**: 32 random bytes from `crypto.randomBytes`. Used
  once in-process to AES-256-GCM encrypt the field, then zeroed.
- **DEK wrap**: AES-256-GCM with the master key, fresh IV per wrap.
  This is a key-wrap, not data encryption — the ciphertext is only
  the wrapped DEK.
- **Wire format** (v1, base64-joined):
  `v1:<keyVersion>:<wrappedDek>:<wrapIv>:<wrapTag>:<iv>:<tag>:<ct>`
- **Blind indexes** unchanged: `HMAC-SHA256(pepper, normalised value)`
  with `OASIS_BIDX_PEPPER` from env.
- **Rotation**: write `OASIS_MASTER_KEY_V2`, flip `OASIS_MASTER_KEY_VERSION=2`,
  run a one-shot `re-wrap` script that decrypts each ciphertext with the
  old version and re-encrypts (re-wrapping the DEK only — the data
  ciphertext can stay if we update the format to allow split rotation;
  for v1 simplicity we re-encrypt fully).

## Consequences

- **Positive**: zero infra cost; encryption runs identically locally,
  in CI, and in production. Wire format is forward-compatible with a
  future move to KMS — only the wrap step changes. Per-record DEKs
  still defeat frequency analysis. Blind indexes still enable lookups
  without decryption. RLS (ADR 0003) still acts as the second wall.
- **Negative**: an attacker who steals **both** the DB *and* the env
  master key sees plaintext. KMS would have prevented that by keeping
  the wrap key inside an HSM. Mitigation: master key lives only in
  Vercel + GH secrets, never on developer machines outside `.env.local`,
  and is rotated annually. Audit logging on every decrypt detects bulk
  exfiltration.
- **Reversible?** Yes. Migration to KMS is a single ADR + a re-wrap
  script that pulls each `wrappedDek`, decrypts with the env master key,
  and re-wraps via `kms:Encrypt`. Wire format gains a `v2:` prefix.

## Operational notes

- `OASIS_MASTER_KEY` MUST be 32 random bytes, base64-encoded
  (44 chars). The encryption module rejects keys of any other length
  to fail loud rather than silently truncate.
- `.env.example` documents key generation:
  `node -e "console.log(crypto.randomBytes(32).toString('base64'))"`
- Production keys are generated by the Director, stored in 1Password,
  and pasted into Vercel — never sent over chat or email.
